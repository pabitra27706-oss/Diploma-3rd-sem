## 5. Rules still in force (do not regress)
The full operating manual is `rule.md`. The load-bearing rules for any future
change:
1. **Branch law:** work only on the current session branch; never create/switch,
   push `main`, force-push, or `git reset --hard`. If `rule.md` and Git disagree
   on the branch name, Git wins — fix the doc.
2. **Release gates (always ask, never assume):** PR, merge, `main` push,
   enabling Pages, deploy, publishing a URL, announcement, money, legal, another
   person's data, waiving a law, changing a recorded decision, changing
   syllabus/answer content needing source verification. Green CI is evidence,
   not authorization.
3. **Decide-once:** anything recorded in `docs/DECISIONS.md` is never re-asked;
   changing it is a gate.
4. **Source integrity:** `_data/<subject>/*.json` PYQ papers + registries are
   byte-frozen by `_data/pyq-integrity.json`. Never edit them or refresh the
   baseline; use derived sidecars. Unknown answers stay ungraded.
5. **Invariants:** zero-build (committed files = what Pages serves); base path
   `/Diploma-3rd-sem/`; no backend/login/analytics/ads/third-party runtime
   request; offline-first and truthful; one source of truth per concern; WCAG
   2.2 AA floor; every displayed number computed from data; every claim true of
   this build; syllabus is the content authority; generated data reproducible
   (never hand-edited); a phase is a folder with a `record.md`.
6. **Definition of done:** checks green, `site-preview` artifact uploaded, docs
   updated, `prompt.md` current, next-chat prompt printed in chat, short report
   — then **stop at the deploy gate**.

## 6. Future work — the canonical process (for anything)
Follow this for every task, big or small:
1. **Verify state first.** `git status`, `git log`, PRs, CI, and the current
   branch name. Read `docs/STATUS.md` + the relevant phase `record.md`. Trust the
   repo and Git, not memory or old summaries.
2. **Classify the decision.** GATE (ask, one Summary batch ≤4 questions) vs
   DECIDE-ONCE (recorded, never re-ask) vs DEFAULT (just do it, log it).
3. **Reuse scan first**, then implement only the current phase's scope. Open or
   update that phase's `record.md` with a "Reused" line and quote `file:line`
   evidence for every claim.
4. **Quality gate without a local browser:** run the documented checks
   (`scripts/check_site.py --strict`, `check_pyq_integrity.py`,
   `validate_pyq.py`, `validate_data.py --check-baseline`, the Node suites,
   `unittest discover`). CI must upload the `site-preview` artifact.
5. **Docs ride with the code:** update the phase record, roadmap status,
   `docs/DECISIONS.md` if anything new, and `prompt.md`.
6. **Report in chat** (what changed, checks run + results, blockers, next step,
   and whether anything was pushed/PR'd/merged/deployed). Always include a
   **"What to test on the website"** section (concrete URLs/steps under
   `/Diploma-3rd-sem/`). Then **print the next-chat prompt** and **wait for the
   owner's "mark as pass" (accept) or "add for later" (record gap + continue)
   before starting the next phase**. Then **stop at the deploy gate**.
7. **Local verification for the owner (branch-specific, push → pull → run):**
   from the checkout, `git push origin <branch>` (no-op if already pushed),
   `git pull --ff-only`, `cd ..`, `python3 -m http.server 8000 --bind
   127.0.0.1`, open `http://127.0.0.1:8000/Diploma-3rd-sem/`. State the
   branch/commit that holds the change; never claim a local preview proves
   deployed or real-device behaviour.

## 9. Addendum — 2026-11-16 site-defect finding (broken live Pages link)

The owner reported the live GitHub Pages link was not working. Investigation:

- **CI is fine** — both session-branch pushes triggered successful Web CI runs;
  the separate `pages-build-deployment` workflow only rebuilds when `main`
  changes (it last ran 4d ago and succeeded).
- **Root cause:** Pages is a Jekyll "legacy" build with **no `.nojekyll` file**.
  Jekyll silently drops underscore-prefixed directories, so `_data/` and
  `_quiz-data/` are excluded from the deployed site. The HTML/CSS/JS load (they
  are under `assets/`), but the JSON the JS fetches (`_data/catalog.json`,
  `_data/practice-days.json`, `_quiz-data/<subject>/unit-N.json`) 404s, leaving
  the page showing "Unavailable" / "Loading today's plan…". It works locally
  because `python -m http.server` serves every file.
- **Fix:** added a root `.nojekyll` (committed on this session branch, not on
  `main`). No Liquid templating exists in the HTML, so disabling Jekyll is safe.
- **To make it live:** `.nojekyll` must reach `main` (Pages builds from `main`);
  that is a merge/deploy GATE. **Resolved 2026-11-16:** merged to `main` (commit
  `d54ba5a`); Pages rebuilt and the live site now loads `_data/`/`_quiz-data/`
  (home shows 5 Subjects / 23 Units / 923 Questions, previously "Unavailable").
