MVC Architecture

MVC and Django's architecture carry 19 of this unit's 30 marks (63%) and appear in all four papers. The question is almost always the same shape: name the three MVC components, then map them onto Django's MVT. Learn the mapping and you have the unit.

MVC Framework and Django MVT (MTV) Architecture

What is MVC?

Model–View–Controller is an architectural pattern that splits an application into three parts with one job each, so that the data layer, the presentation layer and the input-handling layer can change independently. The purpose is separation of concerns: a designer can rewrite the HTML without touching the database queries.

PartResponsibilityIn a shop application
ModelData structure, business rules, database access. Knows nothing about HTML.Product table: name, price, stock
ViewPresentation — renders what the user sees. Displays data, holds no business logic.The product listing page
ControllerReceives user input, decides what happens, fetches from the Model, picks a View.“Add to cart” handler

Benefits to state explicitly in an answer: separation of concerns, reusability (one Model, many Views), parallel development (front-end and back-end teams work at once), and testability (business logic is testable without a browser).

Django follows a renamed variant, MVT (also written MTV: Model–Template–View). Nothing is added or removed — only the names of two layers change, which is exactly what the exam asks you to explain.

Classic MVCDjango MVTFile in a Django projectJob
ModelModelmodels.pySchema and queries, via the ORM
ViewTemplatetemplates/*.htmlHTML presentation, written in DTL
ControllerViewviews.py + urls.pyInput handling, dispatch, choosing a template
The one sentence that carries the marks

“Django calls its controller a view and its view a template, and the URL dispatcher in urls.py performs the routing that a controller would otherwise do.” Everything else in a 4-mark MVT answer is elaboration on this.

The three layers in six lines
# models.py -- the Model
class Product(models.Model):
    name  = models.CharField(max_length=80)
    price = models.DecimalField(max_digits=8, decimal_places=2)

# views.py -- the Controller: fetch, then hand to a Template
def product_list(request):
    return render(request, "products.html", {"products": Product.objects.all()})

# urls.py -- routing from URL to controller
urlpatterns = [path("products/", views.product_list)]
The cycle in one line

browser → urls.py → views.py ↔ models.py/database → template → HttpResponse → browser

Quote this line verbatim in a 3-mark answer: it names every layer in the order the request touches them, and it is the sentence the examiner is looking for.

Django Overview

This section answers the 5-mark “What is Django and why would you use it?” and the 5-mark “steps to create and run a Django project”. Between them and MVC, that is 19 of the unit's 30 marks.

What is Django, Why Use It, and the 6-Step Project Setup

Django is a free, open-source, high-level Python web framework that follows the MVT pattern. Its design philosophy is “batteries included”: features a web application normally needs are built in, so you write application code instead of plumbing.

ReasonWhat it means in practice
Batteries includedORM, admin panel, authentication, sessions, forms and URL routing ship with the framework
ORMWrite Python classes instead of SQL; the same code runs on SQLite, PostgreSQL or MySQL
Automatic adminAn editable CRUD interface for your models appears with no extra code
Security by defaultCSRF tokens, XSS escaping and SQL-injection protection are on unless you disable them
DRY and rapid developmentReusable apps and generic views cut boilerplate; scaffolding via startproject
Scalability and communityUsed by large sites; extensive documentation and third-party packages

The setup question is marked on order and exact command names. Six steps, in this order:

Create and run a Django project
# 1. Create and activate a virtual environment (isolates dependencies)
python -m venv venv
venv\Scripts\activate           # Windows
source venv/bin/activate        # Linux / macOS

# 2. Install Django
pip install django

# 3. Create the project (creates manage.py and a mysite/ package)
django-admin startproject mysite
cd mysite

# 4. Create the database tables Django itself needs
python manage.py migrate

# 5. Create an application inside the project, then register it
python manage.py startapp core
#    add 'core' to INSTALLED_APPS in settings.py

# 6. Run the development server
python manage.py runserver
#    open http://127.0.0.1:8000/
Three details that decide the marks

Project vs application. startproject creates the project — settings and the top-level URLs. startapp creates an application — a self-contained feature. One project holds many apps.

Register the app. startapp alone does nothing until 'core' is added to INSTALLED_APPS in settings.py. This step is frequently forgotten and frequently marked.

migrate before runserver. Without it the built-in auth and admin tables do not exist and the admin page raises an error.

URLs, Views & Templates

9 marks live here — the URL→view→template slice, Django Template Language, and static files. The 2-mark static-files question is the one that goes wrong, so its checklist is below in full.

Django URLs, Views and Templates

Three files make the smallest working page. Trace one request through them: a URL arrives, urls.py matches it to a view function, the view builds a context dictionary and calls render(), and the template turns that context into HTML.

urls.py → views.py → home.html
# myapp/urls.py -- URL patterns to views
from django.urls import path
from . import views

urlpatterns = [
    path("", views.home, name="home"),
    path("product/<int:pk>/", views.detail, name="detail"),
]

# myapp/views.py -- the controller
from django.shortcuts import render, get_object_or_404
from .models import Product

def home(request):
    context = {"title": "Shop", "products": Product.objects.all()}
    return render(request, "home.html", context)

def detail(request, pk):
    product = get_object_or_404(Product, pk=pk)
    return render(request, "detail.html", {"product": product})
templates/home.html — DTL syntax
{% extends "base.html" %}

{% block content %}
  <h1>{{ title }}</h1>

  {% if products %}
    <ul>
      {% for p in products %}
        <li>
          <a href="{% url 'detail' p.pk %}">{{ p.name }}</a>
          – {{ p.price }}
        </li>
      {% empty %}
        <li>No products yet.</li>
      {% endfor %}
    </ul>
  {% else %}
    <p>Nothing to show.</p>
  {% endif %}
{% endblock %}
Piece of DTLMeaning
{{ variable }}Output a value, HTML-escaped by default
{% tag %}A template tag: control flow, inheritance, URL reversing
{# comment #}A template comment — not rendered, not sent to the browser
{% if %} {% elif %} {% else %}Conditional rendering
{% for x in list %} … {% empty %}Loop, with a branch for the empty case
{% extends "base.html" %}Inherit a parent template — template inheritance
{% block content %}A named region the child template fills in
{% url 'name' arg %}Reverse a URL by its name=, instead of hard-coding paths
{% csrf_token %}Insert the hidden CSRF token into a form

Django Static Files

Static files are assets the server sends unchanged: CSS, JavaScript, images, fonts. Django refuses to serve them from the app folder until you configure where they live and how templates may refer to them. The 2-mark answer is a short checklist, and it is the checklist that is marked.

The static files checklist
  1. 'django.contrib.staticfiles' is present in INSTALLED_APPS (it is by default).
  2. STATIC_URL = "static/" is set in settings.py — the URL prefix, not a folder path.
  3. The assets live in myapp/static/myapp/css/style.css. Namespacing by app name avoids collisions.
  4. The template starts with {% load static %}.
  5. The link uses {% static 'myapp/css/style.css' %}, never a hard-coded /static/....
  6. For deployment, run python manage.py collectstatic to copy everything into STATIC_ROOT so the web server can serve it.
Using a static file in a template
{% load static %}
<!DOCTYPE html>
<html>
<head>
  <link rel="stylesheet" href="{% static 'myapp/css/style.css' %}">
</head>
<body>
  <img src="{% static 'myapp/img/logo.png' %}" alt="Logo">
</body>
</html>
The two static-file mistakes

Forgetting {% load static %}. Without it, {% static %} is an unknown tag and the page raises TemplateSyntaxError.

Hard-coding the path. href="/static/css/style.css" breaks the moment STATIC_URL changes. The tag exists precisely so this never appears in a template.

DEBUG = True is what makes runserver serve static files during development. In production DEBUG must be False, and the web server (or whitenoise) serves STATIC_ROOT instead — worth one sentence in a long answer.

Django Forms

Forms are in the syllabus but have carried 0 marks in 2023–2026. This section is deliberately short — enough to answer a 2-mark question if one appears, not a page of boilerplate.

Working with Django Forms and CSRF Protection

A Django Form declares its fields once in Python and then gives you three things for free: HTML rendering of the inputs, server-side validation of what came back, and cleaned data with the right types.

A form, its view, and the template tag
# forms.py
from django import forms

class FeedbackForm(forms.Form):
    name    = forms.CharField(max_length=40)
    email   = forms.EmailField()
    message = forms.CharField(widget=forms.Textarea)

# views.py
def feedback(request):
    if request.method == "POST":
        form = FeedbackForm(request.POST)
        if form.is_valid():                       # validation happens here
            name = form.cleaned_data["name"]      # typed, validated values
            return HttpResponse(f"Thanks, {name}")
    else:
        form = FeedbackForm()                    # empty form for a GET
    return render(request, "feedback.html", {"form": form})

# feedback.html
<form method="post">
  {% csrf_token %}
  {{ form.as_p }}
  <button type="submit">Send</button>
</form>
ElementWhy it is there
forms.FormBase class for a plain HTML form; ModelForm builds one directly from a model
request.method == "POST"Distinguishes a submission from the initial page load
form.is_valid()Runs every field's validation; returns True or False
form.cleaned_dataDictionary of validated values — only available after is_valid()
{% csrf_token %}Inserts a hidden, per-session token that proves the POST came from your own page
What CSRF is, in two sentences

Cross-Site Request Forgery tricks a logged-in user's browser into submitting a request to your site from an attacker's page — the browser attaches the user's session cookie automatically, so the request looks genuine. Django's CsrfViewMiddleware rejects any POST that lacks the matching csrfmiddlewaretoken, which the attacker's page cannot read because of the same-origin policy.

The 2-mark answer

“{% csrf_token %} inserts a hidden token generated per session. On POST, Django checks that the submitted token matches the one in the user's cookie; a request forged from another site cannot supply it, so it is rejected with 403. This protects against Cross-Site Request Forgery.”

Key Definitions

MVC

Model–View–Controller — an architectural pattern that separates an application into data (Model), presentation (View) and input handling (Controller), so each can be modified independently. The benefit is separation of concerns.

MVT / MTV

Model–Template–View — Django's renaming of MVC. The Model is unchanged; MVC's View becomes the Template and MVC's Controller becomes the View. The two names refer to the same three responsibilities.

Django

A free, open-source, high-level Python web framework following the MVT pattern, whose "batteries included" philosophy provides an ORM, an automatic admin interface, authentication, forms, URL routing and a template engine out of the box.

Project vs Application

A project is the whole Django site — configuration plus the root URLconf, one per site. An application is a reusable feature module inside it with its own models, views and templates, registered in INSTALLED_APPS.

URLconf

The URL configuration: a list of path() entries in urls.py that maps URL patterns to view functions, optionally naming each route so it can be reversed with {% url %}.

View Function

A Python function that takes an HttpRequest, performs the required logic, and returns an HttpResponse — usually produced by render() from a template plus a context dictionary. It plays MVC's Controller role.

Template (DTL)

An HTML file with Django Template Language placeholders. {{ var }} outputs a value, {% tag %} is a control tag, and {# #} is a comment. Templates are output-only; they contain no business logic.

Static Files

Assets sent to the browser unchanged: CSS, JavaScript, images and fonts. Served from an app's static/<app>/ folder, referenced through {% static %}, and gathered by collectstatic for production.

STATIC_URL vs STATIC_ROOT

STATIC_URL is the URL prefix under which static files are requested ("static/"). STATIC_ROOT is the filesystem directory into which collectstatic copies them for the production web server.

CSRF

Cross-Site Request Forgery — an attack where another site makes the user's browser submit an authenticated request to your application. Django blocks it by requiring a per-session token, inserted with {% csrf_token %}, on every POST.

ORM

Object–Relational Mapper — the layer that lets you query the database with Python classes and methods instead of SQL. In Django a model class maps to a table and each instance to a row.

Migration

A generated file describing a change to the database schema. makemigrations creates it from your models; migrate applies it, keeping the schema in step with the code.

Multiple Choice Questions

Q 1 In MVC, which component holds the business logic and data rules?
a. Model
b. View
c. Controller
d. Template
Answer: a. Model

The Model defines the schema and the rules for the data. It knows nothing about HTML.

Q 2 Django's MVT pattern is also called …
a. Model–View–Controller
b. Model–Template–View (MTV)
c. Module–View–Table
d. Model–Validator–Template
Answer: b. Model–Template–View (MTV)

Same three roles, two renamed: MVC's view is Django's template, and MVC's controller is Django's view.

Q 3 Which file plays the Controller's role in a Django app?
a. models.py
b. settings.py
c. views.py
d. admin.py
Answer: c. views.py

A view function receives the request, queries models, and returns a rendered template — exactly the controller's job. urls.py dispatches to it.

Q 4 Which command creates a new Django project?
a. python manage.py startproject mysite
b. django-admin startproject mysite
c. django-admin startapp mysite
d. pip install django-project
Answer: b. django-admin startproject mysite

manage.py does not exist yet at this point — it is what startproject creates. startapp makes an application, not a project.

Q 5 What does python manage.py runserver do?
a. Compiles the Python files
b. Creates the database tables
c. Starts the development web server on port 8000
d. Deploys the site to production
Answer: c. starts the development server on port 8000

It serves http://127.0.0.1:8000/ and auto-reloads on code changes. It is not for production. Creating tables is migrate.

Q 6 Where must a new app be registered for Django to use it?
a. urls.py
b. INSTALLED_APPS in settings.py
c. manage.py
d. wsgi.py
Answer: b. INSTALLED_APPS in settings.py

startapp creates the folder; without the INSTALLED_APPS entry Django ignores its models and templates.

Q 7 Which template tag is required before {% static 'css/style.css' %} will work?
a. {% load static %}
b. {% import static %}
c. {% include static %}
d. nothing — it works by default
Answer: a. {% load static %}

Without it, {% static %} is an unknown tag and the template raises TemplateSyntaxError.

Q 8 What is STATIC_URL?
a. the absolute path of the static folder on disk
b. the URL prefix under which static files are served
c. a list of static file names
d. a template variable
Answer: b. the URL prefix

STATIC_URL = "static/" means a file at myapp/static/myapp/css/style.css is served at /static/myapp/css/style.css. The on-disk destination for deployment is STATIC_ROOT.

Q 9 Which tag outputs a variable in Django Template Language?
a. {% varname %}
b. {{ varname }}
c. {# varname #}
d. $varname
Answer: b. {{ varname }}

Double braces output a value (HTML-escaped); {% %} is a tag, and {# #} is a comment.

Q 10 Why is {% csrf_token %} added inside a <form>?
a. It styles the form
b. It validates the email field
c. It stops the form being submitted from another site
d. It encrypts the form data
Answer: c. it defends against cross-site request forgery

It inserts a per-session hidden token that a foreign page cannot know. A POST without a matching token is rejected with 403.

Short Answer Questions

Q 1 What is MVC? Name its three components and their roles.

MVC (Model–View–Controller) is an architectural pattern that separates an application into three components so each can change independently.

Model — the data and business rules; talks to the database. View — the presentation layer; renders what the user sees. Controller — receives user input, coordinates the Model and View, and decides what happens next.

The benefit is separation of concerns: presentation can be redesigned without touching data logic, and the business logic is testable without a browser.

Q 2 How does Django's MVT differ from classic MVC?

The three roles are identical; two are renamed. Django's Template does what MVC calls the View, and Django's View does what MVC calls the Controller. The Model keeps its name.

This means models.py ↔ Model, templates/*.html ↔ View, and views.py plus the urls.py dispatcher ↔ Controller. Django also calls the pattern MTV for the same reason.

Q 3 Why is Django called a "batteries included" framework?

Because features that a web application normally has to be assembled from separate libraries ship with the framework itself: an ORM, an automatic admin interface, authentication and sessions, forms with validation, URL routing, template engine, and built-in protection against CSRF, XSS and SQL injection. You write application code rather than assembling infrastructure.

Q 4 Differentiate a Django project from a Django application.

A project is the whole site: it is created with django-admin startproject and holds settings.py, the root urls.py and the WSGI/ASGI entry points. There is exactly one per site.

An application is a self-contained feature module created with python manage.py startapp, containing its own models.py, views.py, templates and admin registration. A project can contain many apps, and an app is reusable across projects — but only after it is added to INSTALLED_APPS.

Q 5 What are static files and how are they configured in Django?

Static files are assets served to the browser without modification: CSS, JavaScript, images and fonts. They are configured by four steps: 'django.contrib.staticfiles' in INSTALLED_APPS; STATIC_URL = "static/" in settings.py; the assets placed in an app's static/ folder; and {% load static %} followed by {% static 'path' %} in the template. For deployment, collectstatic gathers everything into STATIC_ROOT.

Q 6 What is CSRF and how does Django prevent it?

Cross-Site Request Forgery is an attack in which a page on another site causes the user's browser to submit a request to your application. The browser attaches the user's session cookie automatically, so the request looks authenticated.

Django's CsrfViewMiddleware requires every POST to carry a hidden csrfmiddlewaretoken, inserted by {% csrf_token %}. The token is per session and the attacking page cannot read it because of the same-origin policy, so the request is rejected with 403.

Q 3 (8 marks) a) Explain URLs, views and templates in Django with an example. b) Explain static files and how they are configured.

a) The three layers. urls.py maps a URL pattern to a view function using path(); the view receives the request, obtains data, and calls render(request, template, context); the template turns the context dictionary into HTML using Django Template Language.

# urls.py
from django.urls import path
from . import views
urlpatterns = [path("product/<int:pk>/", views.detail, name="detail")]

# views.py
def detail(request, pk):
    product = get_object_or_404(Product, pk=pk)
    return render(request, "detail.html", {"product": product})

# templates/detail.html
<h1>{{ product.name }}</h1>
{% if product.in_stock %}<p>In stock</p>{% endif %}

DTL: {{ var }} outputs a value (escaped); {% tag %} is a tag; {# comment #} is a comment. Key tags are {% for %} with {% empty %}, {% if %}, {% extends %} and {% block %} for template inheritance, and {% url %} to reverse a named route.

b) Static files. CSS, JavaScript, images and fonts served unchanged. Configuration:

# settings.py
INSTALLED_APPS = [..., "django.contrib.staticfiles"]
STATIC_URL = "static/"

# template
{% load static %}
<link rel="stylesheet" href="{% static 'myapp/css/style.css' %}">

# deployment
python manage.py collectstatic

Files live in myapp/static/myapp/..., namespaced by app to avoid collisions. STATIC_URL is the URL prefix, not a disk path; STATIC_ROOT is where collectstatic gathers files for the web server. In development DEBUG = True lets runserver serve them; in production DEBUG is False and the web server serves them. Two common errors: forgetting {% load static %} (a TemplateSyntaxError) and hard-coding /static/... instead of using the tag.

def feedback(request):

Quick Revision

The unit in 10 points
  • MVC splits an application into Model (data), View (presentation) and Controller (input). The driver is separation of concerns.
  • Django uses MVT. Model stays; MVC's View becomes Django's Template; MVC's Controller becomes Django's View.
  • models.py ↔ Model, templates/*.html ↔ View, views.py + urls.py ↔ Controller.
  • Request lifecycle: browser → urls.py → views.py ↔ models.py/DB → template → HttpResponse.
  • Six setup steps: venv → pip install django → startproject → migrate → startapp (+ INSTALLED_APPS) → runserver.
  • A project is the site; an app is a reusable feature module inside it. One project, many apps.
  • DTL: {{ var }} outputs, {% tag %} controls, {# #} comments. {% extends %} and {% block %} give template inheritance.
  • Static files need four things: the staticfiles app, STATIC_URL, the app's static/<app>/ folder, and {% load static %} + {% static %}.
  • STATIC_URL is a URL prefix; STATIC_ROOT is the disk folder collectstatic fills for production.
  • {% csrf_token %} is mandatory in every POST form; without it Django returns 403.
Facts examiners award marks for
  • Django's claim to MVC is the mapping, not the acronym — name the two renamed layers explicitly.
  • Django's view is the controller and its template is the view. Most candidates invert this.
  • An app does nothing until it is added to INSTALLED_APPS.
  • django-admin startproject comes before manage.py exists; manage.py startapp comes after.
  • migrate creates Django's own tables. Without it, /admin/ fails with "no such table".
  • runserver is development-only; production uses WSGI/ASGI (gunicorn, uwsgi) with DEBUG = False.
  • CSRF protects against forged requests, not against weak passwords or injected script (that is XSS).
Where marks are commonly lost
  • Saying "Django's View is MVC's View". It is not — Django's View is the Controller.
  • Writing "Django is a programming language" or "a database". It is a web framework.
  • Listing the six steps out of order, or omitting migrate.
  • Hard-coding /static/css/style.css in a template instead of {% static %}.
  • Forgetting {% load static %}, which is a TemplateSyntaxError.
  • Calling STATIC_URL a folder path. It is the URL prefix.
  • Answering "Is Django better than Flask?" with "yes" — the marked answer is the trade-off.
